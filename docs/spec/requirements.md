# 要件定義v2（2026-11-18）

前回の要件定義（20261113 要件定義他 メモ）の構成を保ち、11/17の画面レビュー会議の要約、Figmaのコメント（#2〜#10）、11/19〜11/20に決めた事項で修正した版。旧版はメモとして残している。判定は「維持」「変更」「削除」「追加」で示す。

## 目的

技大祭の落とし物管理を楽にする。特に、落とし物を見つけた来場者の負担を最小にする。（維持）

## 背景・課題

- 落とし物の管理が、実行委にとって大変である
- 落とし主は、落とし物が届けられているかわからない
- 拾得者（来場者）が、届けるのを面倒に感じてしまう

（維持）

## 開発の進め方（追加）

- 方針は「引き算」。画面と機能を減らし、各画面に「いる/いらない」を付けて絞る。
- 作業は3つの段階に分ける。まずA（核）を最後まで通して動かし、動いたらB（簡単な形で後から足すもの）を1つずつ足す。マキシマム版（C）はその後。
  - A（核）: 「拾う → 回収 → 登録 → 届け出 → 照合 → 受渡」の一本道が動くための機能。これが動けばミニマム版として成立する。
  - B: ミニマム版には入れるが、Aの動作確認が済んでから足すもの。最初は手作業や簡単な形で代えられる。
  - C（マキシマム版）: PCの管理画面とAIの利用（照合を含む）など。
- ミニマム版の作業はすべて人が行い、AIは使わず、スマホの画面だけで作る。

## ユーザー

- 来場者（一般権限）: 拾得者、落とし主（維持）
- 実行委員（管理者権限）: 操作権限は全員一律。ミニマム版はスマホで操作する（変更）

## 状態遷移

旧版の遷移を維持する（仮登録済 → 回収済 → 本登録済 → 受渡済、不明への遷移と元の状態へ戻す操作、直接登録は最初から本登録済）。変更は次の点。

- 「回収済」にする操作は、ボックスのQRを読み取って行う（変更）
- 「仮登録済 / 回収済 → 受渡済」（途中受渡）の遷移はなくす（削除）
- 「この登録は無効」の状態は作らない。「不明」は残す（変更）
- 時間経過で「不明」にする自動判定はなくす。回収時に数が合わず見当たらなかった分を「不明」にする（B）。手動で不明にする操作はA（変更）

## 制約・前提

- 来場者約10,000人、実行委約200人、2日間。ハッカソンで作る（維持）
- 落とし物BOXを各所に設置する。QRはボックスの裏に貼る案が出ている（変更）
- 来場者にアプリのインストールやアカウント登録を求めない。来場者への連絡はメールで行う（維持）
- 拾得者の位置情報は使わない。QRから箱を特定して場所を記録する（維持）
- 混雑時の不安定な回線でも使える（維持）
- 操作履歴は残さない。誤操作や不正があっても、誰が行ったか、誰が個人情報を見たかは追えない。このリスクは運営が了承する（維持）
- QRをいたずらで読まれると実行委員の負担が増える。対策はシステムを作ったあとでもできるため後回し（追加）
- ボックスの場所のマップ案内は、位置情報の取得が難しいためマキシマム版（追加）

## 決定事項と残りの確認事項

### 決まったこと（11/19〜11/20）

- 管理番号: 物の本登録のときに、物に対して自動で付ける独立の番号。実行委員と落とし主が同じ番号を使う（要求4、6）。
- 保管場所の伝え方: メールに載せる（要求6）。
- 本登録でのAI: ミニマム版には入れない（要求4）。
- 照合: ミニマム版は人手、マキシマム版はAIで行う（要求9）。
- 実行委員への通知: アプリ内で閲覧できる（要求1）。
- 途中受渡: 想定しない。要求15を削除した。
- 受け渡し済みの表示: PC用の画面を使い回し、スマホで見られる形にする（要求10）。
- 不明の付け方: 時間経過（30分）ではなく、回収時に数が合わず見当たらなかった分を不明にする（要求12）。
- ミニマム版の作り方: A（核）を先に最後まで通し、動いてからBを1つずつ足す。
- 拾得者の通知: 拾得者の負担を減らすため、ボタンを押させず、QRを読んで画面を開いた時点で通知する（要求1）。
- カテゴリ: 選択式（単一選択、必須）に「その他」を設け、「その他」のときは自由記述を必須にする。「その他」は件数を出さない。届け出と本登録で同じ選択肢を使う（要求4、7）。

### 残りの確認事項

- Figmaの付箋の見落とし確認: Figmaの画面の上には「いらない」と書かれた付箋が貼ってある。今回の修正は、会議要約とFigmaのコメント7件をもとにしていて、付箋は1枚ずつ確認していない。付箋だけにあって会議で話に出ていない削除があれば、この文書に抜けている。全部確認して洗い出すか、このまま進めるか決める。
- 仕様書の整理（下の提案の方針でよいか確認する）。
- Bに入れた項目（撮影後の確認画面、数が合わないときの確認と不明判定、届け出の取り消し、ホーム画面）の振り分けでよいか。
- カテゴリの選択肢の最終版（上の例でよいか）。

## 提案: 仕様書（基本設計）の整理の仕方

- ファイルは分けず、1つの基本設計書にする。ミニマム版はマキシマム版の一部で、共通部分が大半のため、2つに分けると同じ内容を二重に直すことになる。
- 機能一覧（F-xx）と画面一覧（S-xx）に「版」の列（A / B / C）を足す。画面一覧には「状態」の列（残す / 変更 / 削除 / 新規）も足す。
- 削除した画面は一覧から消さず、「削除した画面」の欄に理由つきで移す。後から「なぜ消したか」を聞かれたときに答えられる。
- 画面遷移図と業務フローは、Aの図を基準にして、Bとマキシマム版（C）で足す部分を色分けして重ねる。途中受渡と無効の流れは、図から消す。
- 作業の順番は、(1)この要件定義の要求1〜16と機能一覧（F-xx）を対応づけ直す、(2)Figmaの画面ID（S-xx）を基準に画面一覧を作り直して版と状態を付ける、(3)状態遷移図と業務フローを直す、(4)詳細設計に送る項目を更新する（管理番号の採番形式、カテゴリの選択肢の一覧など）、の順。
